01

第一版，恢复到能开始工作的程度

依据你的补充：启动到正确目录就是首轮目标；恢复上次文件与 AI 历史可以后补。完成角标仍属于核心需求。

必须成立

  • 项目对应一个逻辑工作区组；左 Neovim、右一个 AI CLI。
  • 两个独立 foot，切换时各自记忆输入法状态。
  • 重启后按需打开项目，程序与工作目录正确。
  • 反复打开同一项目，不重复创建窗口。
  • AI 主回复结束，顶栏对应工作区显示待查看标记。

允许后补

  • Neovim 文件集合、光标、编辑器内部布局。
  • Codex / Claude 精确续接上次会话。
  • 临时终端、终端滚屏和更复杂的桌面布局。
  • 未保存文本、意外断电后的恢复。

重启后的初始中英文状态不纳入第一版；已运行窗口之间的独立状态必须回归验证。

02

沿用现有结构，把责任接清楚

保留两扇独立 foot，桌面负责左右分屏。编辑器沿用 tmux；AI 后台可沿用 tmux，或验证后接入 Herdr direct attach。重启后由项目配方协调恢复，各后台负责自己的应用。

输入法边界就是 foot 窗口

现有 Fcitx5 设置 ShareInputState=No 与 resetStateWhenFocusIn=No，符合你已验证的体验。两个 tmux pane 放进同一 foot，不能自然提供两个桌面输入上下文。

Neovim 的 im-select.nvim 还有模式切换行为；恢复后需检查 Normal / Insert / 焦点切换是否符合原习惯。

“session”实际有四种

桌面 session当前 Hyprland 实例、显示器与窗口；重启会重新创建。 → 工作区与窗口位置。

tmux session服务器活着时，终端程序可以继续运行；不是进程跨重启存活。 → 终端进程与重连。

Neovim session文件、窗口布局等编辑器状态；不是未保存文本的完整备份。 → 编辑现场。

AI sessionCLI 自己维护的对话与会话 ID；恢复历史不代表恢复中途运行的工具进程。 → 对话上下文。

03

半成品已经做到哪里

“已有”来自仓库与已安装文件；“缺口”是静态代码推导。本次没有切换你的桌面或启动新的 AI 会话。

部分已有能力还缺什么
项目启动coding-workspace [目录] 已安装；规范化路径、派生 hash / app ID、加锁、识别已有窗口、打开两个 foot。持久文件仅有组号；没有可浏览的项目目录清单，也没有项目级 AI 选择。
工作区组ten_workspaces 跨显示器切换、移动、热插拔；Quickshell 已有总览。显示器 slot 只在当前 compositor 会话内稳定，不能把 native workspace ID 当永久项目身份。
终端保活项目两侧分别进入 tmux；普通 ten-terminal 仍是裸 shell。resurrect / continuum 已启用。自动恢复与显式启动可能竞争；AI 不在默认恢复程序清单中。
NeovimLazyVim 已带 persistence.nvim，锁文件与本机代码均可确认。入口启动 nvim .；未发现项目启动自动加载 persistence 的接线。
AI / 顶栏default-agent 固定转发 Codex；顶栏展示工作区占用与焦点。没有完成事件到顶栏的通道，也没有自动 resume。
优先修正：窗口与工作区之间的五处协调问题
  1. 左右窗口可能分居两屏：place_new() 将新 tiled 窗口分配到负载较小的显示器。为受管的 ten-coding-* 提供例外，由项目协调器指定同一显示器。
  2. 重复调用还会重排：末尾无条件向左 swap 与设置 splitratio。两侧都存在时只聚焦；初次成对创建或显式“重排”时再布局。
  3. 空组占位被视为占用：默认 1–5 等 persistent 组出现在 workspace 列表中，入口按“存在”排除。应结合项目登记与实际窗口判断，而非跳过所有空占位。
  4. 自定义 app ID 影响快捷键：复制粘贴只识别 window.class == "foot"，项目却使用 ten-coding-*。应一并识别，避免 Super+C 被转发为 Ctrl+C 中断程序。
  5. 异步启动竞态：启动时先登记目标并显式路由，不依赖当前工作区一直不变。AI 映射超时应报部分失败；锁文件 FD 是否传给长寿命子进程需核实并显式关闭。

恢复插件为什么没有自然接上

resurrect 的 @resurrect-strategy-nvim 'session' 在本机检查项目里的 Session.vim；persistence 则默认保存到 stdpath("state")/sessions/，并按 cwd / 分支区分。两者不共享恢复入口。

本机 resurrect 默认程序清单有 nvim，没有 codex / claude。恢复的 AI pane 可能只剩 shell；tmux new-session -A 会连接已有 session，不会因附带启动命令就自动重跑 AI。

tmux 基线路径：项目专用 tmux server / 配置使用独立 socket，例如 -L ten-coding，先不启用自动 resurrect / continuum；普通 tmux 保持现状。项目冷启动由协调器统一负责。若选用 Herdr，AI 的恢复交给 Herdr，协调器只负责调用与桌面绑定，避免两套恢复逻辑竞争。

04

恢复深度，按收益逐层加

层级恢复什么负责者 / 相对难度建议
A · 重新打开工作区、两个 foot、cwd、nvim / AI项目协调器 · 低至中第一版验收
B · 本次开机重连重新连接仍然存活的程序编辑器 tmux；AI tmux / Herdr验证后台与 UWSM 生命周期
C · 内容续接编辑文件 / 布局、AI 历史persistence + CLI resume / Herdr · 中紧随其后
D · 更多现场临时窗口、滚屏、任意布局、未保存文本多个保存器与策略 · 高单独增量

难度为结合当前仓库的判断，非工时承诺。这里的重启指冷启动，程序需要重新启动。

Neovim：先用已有 persistence

当前可在正确目录启动后按 <leader>qs 恢复该目录 session。第一版继续正常打开 nvim；后续仅对项目入口启用自动 load。

先保证 cwd 正确、插件已加载；无存档则正常打开项目。按 cwd / 分支恢复，避免 load({ last = true }) 接到其他项目。

默认正常退出时保存，需至少一个具名文件 buffer；未保存文本和崩溃另行处理。内嵌 Claude 插件可保留，但不承担两个桌面窗口的管理。

AI：先启动，再续接

以下参数已用本机 CLI 帮助核对：

# 都先进入项目根目录
codex resume              # 选择会话
codex resume --last       # 当前目录最近会话
codex resume SESSION_ID   # 精确恢复

claude --continue        # 当前目录最近会话
claude --resume SESSION_ID

首次无历史直接启动；精确恢复失败时提供选择 / 新建，不无限重试。应用自己维护记录，项目登记册只引用 ID。

tmux 的适用范围与生命周期

沿用 tmux 的基线路径适合“一侧一个 session，每个 session 一个主要 pane”。Herdr 路径仅编辑器保留 tmux，AI 使用 direct attach。两扇 foot 不要连接同一 session 后再切 pane，否则视图与焦点会耦合。tmux 上游 ↗

服务器与进程活着时能重连；重启会结束进程。resurrect 是重建布局与重新启动支持的程序，不是保存进程内存。如果只验收第一版 A 层，直接 foot 启动程序也可行；保留 tmux 是为了复用已有代码并获得 B 层收益。

项目专用配置保留 TERM / truecolor / focus-events，只简化状态栏与自动恢复。每个进程显式绑定项目身份，不能反复改 tmux 全局环境来代表不同项目。桌面实例变化后刷新 Wayland 等环境，并重新绑定窗口。

首次 server 由 uwsm app 下的 foot 派生，关闭 scope 时是否一并结束需实测；若会被清理，再交给独立用户服务。第一版不承诺跨注销保活。

05

“回复好了”是一条事件

把 CLI 的明确完成事件转成项目未读状态。持续输出、shell 退出、终端标题和 bell 都不能准确代表“一轮回复结束”。

Codex · 最小事件通道

使用 notify 的 agent-turn-complete。脚本从一个 JSON 参数读取 thread-id、turn-id、cwd，登记主回复完成。

# 配置草案；ten-ai-event 尚未实现
# 用户级 ~/.codex/config.toml
notify = ["ten-ai-event", "codex"]

项目级配置不能覆盖 notify。外部回调不要求弹系统通知；TUI 通知是另一条通道，关闭前要保留权限等待的可见性。

notify 文档 ↗ · 配置作用域 ↗

Claude · Stop hook

使用主 agent 的 Stop，从 stdin JSON 读取 session_id / cwd。不用 PostToolUse 或 SubagentStop 代替。

{ "hooks": { "Stop": [{ "hooks": [{
  "type": "command",
  "command": "ten-ai-event claude"
}]}]}}

草案需合并现有 settings，保留其他 hooks。Stop 不覆盖用户中断；错误另有事件。观察脚本不输出控制指令，不阻塞 AI。

Claude Stop 文档 ↗

完成、已读、等待审批：三种语义分开处理

完成只指主回复结束：不是测试通过、代码提交或全部后台工作结束。已有 Stop hooks 若强制续跑，需验证是否提前亮标记；不能按 stop_hook_active=true 一概丢弃，否则可能漏最终回复。

已读跟随 AI 窗口：只到同组 Neovim 不清除。组号仍切换工作区；未读标记可单独点击，聚焦 AI 后清除。AI 已获焦点时可直接视为已读。多屏“可见”不等于“已读”。

审批等待另行扩展：用琥珀色“待操作”，不冒充完成。Codex notify 只有完成事件；当前 hooks 支持 PermissionRequest / UserPromptSubmit / Interrupt 等，可后续补齐。第一版可以没有“运行中”状态，不能把上次完成标记当作当前运行状态。

当前 Codex 已支持 hooks，不能再以“没有 hooks”为前提。新或变更的非托管 hook 需在 CLI /hooks 中信任；事件行为仍应以安装版本验收。Codex hooks ↗

事件如何找到正确工作区，而不误标你当前的项目

启动时绑定 project_id，附工具类型、AI session ID、启动世代与事件 ID。由项目对应的 AI app ID 找 live window，再查询其当前 workspace，折叠为逻辑 group。不要使用“收到事件时的 active workspace”。

拖动 AI 窗口后标记跟随新组，同组多个未读聚合。窗口关闭而 tmux / Herdr 后台仍活着时，未读挂在项目上，项目列表继续显示；重新打开后绑定顶栏。

Codex 用 thread-id + turn-id 去重；Claude 若无稳定 turn ID，先做布尔未读，不显示精确条数。后续在 session / 启动世代内序列化事件，避免重复、迟到事件覆盖新的已读状态。

一个写入端带锁更新小型 JSON，使用临时文件原子替换；启动时先建空状态文件。Quickshell 用 FileView.watchChanges 与 onFileChanged: reload() 读取，不持续扫描 CLI 对话日志。FileView 文档 ↗

未读放在 $XDG_RUNTIME_DIR/ten-coding/：Quickshell 重启可重读，整机重启清空。只记录事件元信息，不复制提问或 AI 正文；无项目绑定的普通 CLI 默认忽略。

若改用 Herdr：

以上是直接接 CLI 完成事件的基线。Herdr 可提供统一状态订阅，但 Codex / Claude 的屏幕状态检测不等于精确的回复完成事件。顶栏仍需 TenOS 自己维护未读与窗口映射；实现时选定状态来源，精确完成提示可继续使用 CLI hooks。查看接入边界 →

一个入口，两个入口位置

先补好现有命令，再给 Quickshell 总览增加“项目”列表。运行中的工作区与未打开的项目是两种对象；重启后列表不能依赖当前桌面窗口。

目录里打开

# 现有命令名；当前实现仍有上述缺口
coding-workspace ~/codes/nixos

# 建议扩展，尚不可用
coding-workspace open --agent claude .
coding-workspace list --json

保留 coding-workspace [目录] 兼容入口。默认按目录对应项目打开；AI 选择写入记录，后续沿用。

桌面里打开

项目列表：名称、路径、AI 类型、运行 / 未打开 / 待查看状态。点击未打开项目调用同一命令，运行项目则聚焦。

现有总览：继续管理运行中的窗口；新增项目入口不要求先有空工作区。从用户明确打开过的项目登记，不扫描整个磁盘。

打开项目的确定性规则
  1. 规范化目录并检查存在；读取或新建项目配方，按项目加锁。
  2. 两侧窗口都在就聚焦；只缺一侧就补；都没有才分配组。不同项目分配组还需短暂的全局分配锁。
  3. 默认当前显示器，同屏左右；偏好屏缺失则回退当前屏。组号冲突时改选空闲组。
  4. 按角色选择 tmux 或 Herdr：后台 session 活着就重接，缺失就用正确 cwd 启动应用。存在但应用退出时，显示明确重启操作，不能盲目向仍有任务的 pane 发命令。
  5. 确认窗口映射与初始左右布局；已有临时窗口不改。部分失败保留成功一侧，再次执行可补齐。
  6. 成功后更新项目登记与运行绑定，释放锁。失效目录保留条目并说明原因，不反复启动。

临时窗口第一版不登记、不恢复，同次开机已经存在的仍保留。以后可显式提升为“第三个受管角色”，比自动推断任意程序更可控。

07

Herdr：可借用的 AI 后台

调查对象为 herdrdev/herdr ↗；本次查看的源码标注 0.9.0。它把真实 AI 终端、状态检测与控制接口放进一个后台服务。下面区分已文档化能力、TenOS 接入设计和仍需实测的部分。

更新后的选择：先验证 Herdr direct attach

只做项目恢复与完成角标，现有 tmux 仍可承担。若还要 Claude ↔ Codex 协作、统一状态与远程管理，优先验证 Herdr 管 AI，Hyprland 管窗口。多 agent 协作属于扩展能力，不扩大第一版“每项目通常一个 AI”的最低要求。

“agent 对话”到底做了什么

主 agent 调用 Herdr，给另一个 agent 输入提示词、等待并读取输出。双方各有自己的上下文；分工、任务关联和是否继续追问，需要指令或脚本约定。自动化接口 ↗

示例与边界：能传话，不代表已完成可靠编排
# 示例：假设 reviewer 已启动并可接收任务
herdr agent prompt reviewer \
  "审查任务 T42 的 diff；结果写入约定文件" \
  --wait --timeout 120000

herdr agent read reviewer --source recent-unwrapped --lines 120

agent prompt 处理 bracketed paste 与 Enter；对已 blocked 的 agent 返回错误，不把普通提示词塞进审批对话。需先读取界面，再决定如何响应。

等待不绑定精确 turn：对方若原本在工作，当前那轮结束可能满足等待。超时也不证明没收到输入；重试前先核对，避免重复派单。长回复可写 Markdown 文件，再回报文件路径，避免只读到终端最后几行。

建议一项目保留主 agent，审查者按需启动。一次任务带 task ID、输入文件、结果文件与成功条件；审查者默认只读，修改型并行工作用独立 worktree，最终整合由一个角色负责。限制讨论轮数；Herdr 不自动解决共享文件冲突或无限讨论。

桌面桥接仍需自己做：身份、未读、恢复与并发

身份：登记项目、Herdr server 命名空间、terminal / agent、foot app ID 的对应关系，再查 Hyprland 当前组。agent 名是活跃别名，进程退出后可能失效；跨重启不能仅存这个名字当恢复身份。不同 server 的 ID 需带命名空间。

状态与已读：订阅 pane.agent_status_changed 等事件，映射到顶栏。Herdr CLI 与每个 TUI 客户端的已读视角可能不同；TenOS 应维护自己的未读，并由实际 AI foot 焦点确认。不能把 Herdr 内部当前 pane 当成桌面当前窗口。

重新连接：先建立事件订阅，再读取 session.snapshot 并应用暂存事件；断线后重新取快照，避免漏掉启动期间的变化。Herdr 检测状态与 CLI 完成 hooks 若并存，分别表达“运行状态”和“明确完成事件”，不能同时争写同一个状态字段。

恢复与保活：coding-workspace 负责找回或创建 AI、打开 direct attach；Neovim 侧保持现有路径。Herdr 的全会话恢复可能重开多个项目，需要确认是否符合“只打开选中项目”，必要时选好命名 session 边界或调整自动恢复策略。

并发输入：一个可写 direct attach 不等于自动获得任务级互斥。人在输入时，其他 agent 的 prompt 仍需协调；避免人和 agent 同时编辑同一输入行。
