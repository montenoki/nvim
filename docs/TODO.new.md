# 想法与待办

以下是四种 Markdown TODO 写法，用同一个“整理编辑器配置”场景演示。
任务、完成状态和日期均为示例，不代表项目实际进度或承诺。选一种作为主结构即可，
不需要把同一份任务在四种结构里各维护一次。

## 先约定几个符号

| 表达什么   | 写法                                   | 含义                                    |
| ---------- | -------------------------------------- | --------------------------------------- |
| 分类与层级 | `## 语言支持`、`### 配置文件`          | 组织内容，不表示任务状态                |
| 待办       | `- [ ] 补齐 TOML 支持`                 | 还没有完成                              |
| 完成       | `- [x] 补齐 TOML 支持`                 | 已满足验收条件                          |
| 优先级     | `[P1]`、`[P2]`、`[P3]`                 | P1 优先处理；P2 正常排期；P3 有余力再做 |
| 执行状态   | `状态：进行中`、`状态：阻塞`           | 描述进展，与优先级分开                  |
| 无序子任务 | 缩进后的 `- [ ]`                       | 表示归属，不强制执行顺序                |
| 有序步骤   | `1. [ ]`、`2. [ ]`                     | 表示预期执行顺序                        |
| 时间       | `开始：2026-10-01`、`截止：2026-10-08` | 区分开始、复查、截止和完成时间          |

这里只使用普通标题、列表、表格和 GFM 任务复选框，不依赖专用任务插件。
`[P1]` 和状态文字是自己的约定，不会自动排序、提醒或改变复选框。

**标题层级、优先级、子任务层级是三件事。** 例如“语言支持 → 配置文件”是分类，
`[P1]` 是处理优先级，“调查 → 配置 → 验证”是任务拆解。

## 方案二：每项任务一张卡片

**适合：约束多、需要讨论、需要明确验收的复杂任务。**
任务使用稳定编号，标题负责定位，复选框负责完成状态；编号不会因为排序改变。

## 方案三：总览表 + 任务详情

**适合：任务较多，需要同时比较优先级、负责人、依赖和截止日。**
表格负责排期与状态；长说明放到下面，避免把多段文字和子任务塞进单元格。

## 方案四：里程碑 + 有序交付清单

**适合：有明确交付时间的重构、迁移、上线准备。**
按阶段组织任务，阶段内的独立事项用无序列表，需要前后衔接的操作用有序列表。

  - [x] 确认本轮不处理的内容。
  - **完成时间**：2026-10-02。
  - **产出**：一份可直接据此实施的工具清单。

### M2：配置可用，目标日期 2026-10-08

## 怎么选

| 你的主要需求                         | 建议方案              |
| ------------------------------------ | --------------------- |
| 快速记录，日常自己维护               | 方案一：嵌套清单      |
| 每个任务都有较多约束、讨论和验收     | 方案二：任务卡片      |
| 同时管理许多任务，需要总览与依赖关系 | 方案三：总览表 + 详情 |
| 围绕某次交付按时间推进               | 方案四：里程碑计划    |

**按当前仓库的用法，建议采用“方案一作为目录，复杂任务使用方案二展开”。**
例如普通键位调整用一条清单即可，窗口移动逻辑重构则单独写目标、约束、步骤和验收。
有一次明确部署计划时，再给相关任务补里程碑，不必把所有想法都排到时间表里。

## 容易写乱的地方

- **不要用 `### - [ ] 待办` 代替任务清单。** 它是标题，通常不会变成可勾选任务。
  应写成标题下一行的 `- [ ] 待办`，标题和列表之间空一行。
- **父任务不会自动完成。** 子任务全部勾选后，还要核对父任务的验收条件。
- **有序编号不代表依赖管理。** 遇到阻塞，仍需明确写“依赖谁、何时解除”。
- **约束和备注不用都加复选框。** “不自动下载依赖”是持续约束；
  “验证启动时没有下载行为”才是可以完成的检查项。
- **避免一条任务包含多个独立结果。** “补齐语言支持并调整主题并部署”应拆开，
  否则做完一部分时无法准确标记状态。
- **取消不等于完成。** 可写 `- ~~不再执行的任务~~ — 已取消：原因`，移出待办统计。
- **尽量写绝对日期。** “下周五”容易过期；改写为 `复查：2026-10-09`。
- **日期写清用途。** 截止日是交付要求，复查日只是回来检查进展，实际完成日用于记录结果。
- **缩进表示归属。** 任务下面的备注、约束、有序步骤要保持缩进；
  否则渲染后可能变成平级任务或代码块。

## 一个可复制的最小模板

```markdown
## 分类

- [ ] **[P1] 用动词描述具体结果**
  - **状态**：待开始
  - **时间**：开始 YYYY-MM-DD；截止 YYYY-MM-DD；复查 YYYY-MM-DD
  - **依赖**：无 / 前置任务编号
  - **约束**：必须遵守的规则，以及本轮不做的内容。
  - **子任务**：
    1. [ ] 调查并确认范围。
    2. [ ] 实施修改。
    3. [ ] 验证结果。
  - **验收**：什么结果出现后，才允许勾选父任务。
  - **备注**：背景、疑问或已作出的决定。
  - **完成记录**：完成后补实际日期和结果链接。
```

模板里的可选字段按需删除，不必为了格式完整而给每项任务填一整张表。
